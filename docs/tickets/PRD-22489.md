## Current state

- `datto-rmm-mcp@main` (34eb533) is a FastMCP server with 6 tools (`src/datto_rmm_mcp/server.py:150-155`): `dattormm_get_devices`, `dattormm_get_components`, `dattormm_run_component`, `dattormm_get_job_status`, `dattormm_get_alerts`, `dattormm_resolve_alert`.
- **List components already works**: `dattormm_get_components` returns uid, name, description and the variables each component takes (`src/datto_rmm_mcp/tools/components.py:16-26`, endpoint verified live per its module docstring `components.py:3-8`).
- **`dattormm_run_component` sends a request body that does not match Datto's OpenAPI.** It builds `{"componentUid": ..., "<name>": "<value>", ...}` (`src/datto_rmm_mcp/tools/jobs.py:70-72`). The official spec (`PUT /v2/device/{deviceUid}/quickjob`) requires `{"jobName": <string>, "jobComponent": {"componentUid": <string>, "variables": [{"name": <string>, "value": <string>}]}}`, with `jobName` and `jobComponent` both required, and answers `{"job": {"uid", "status", ...}, "jobComponents": [...]}`. The README already records that this call "has never been executed" and that blind probes got `{"detail":"Failed to read request"}` (`README.md` Known Gaps, quickjob bullet) — consistent with a wrong body shape. So variables cannot be passed correctly today (Done when 1).
- **No tool reads job output.** `dattormm_get_job_status` returns only `active`/`completed` (`src/datto_rmm_mcp/tools/jobs.py:79-99`). Its docstring, the server `instructions` (`server.py:133-150`) and README Known Gaps state that Datto offers no success/failure or stdout/stderr through the API. The current official spec contradicts this: it has `GET /v2/job/{jobUid}/results/{deviceUid}` (returns `jobDeploymentStatus` ∈ Expired/Pending/Running/Success/Warning/Retired/Failure and per-component `componentStatus` ∈ Success/Failure, `hasStdOut`, `hasStdErr`), `GET /v2/job/{jobUid}/results/{deviceUid}/stdout` and `.../stderr` (each returns `[{componentUid, componentName, stdData}]`). The README itself says the v14.0.0 release notes claim these endpoints and that they "could not be traced" — the spec we read now names them, so the old caveat is resolved on paper; it is still **not field-verified** (no sandbox account).
- **Test connection**: the platform asks owl's health probe, which makes one real read-only tool call that owl picks (`mb-platform-agent` `service/integrations/connectionTest.ts`, PRD-22065 note at lines 18-22; `outcomeForProbe`). Owl's probe only calls a tool when the integration has `health_tool` set and `health_enabled=true`; otherwise the status is `unknown` and the platform shows "Handshake only" (`mcp-service-gateway` `mcp-manager/mcp_manager/health/probe.py`, `_l1_l2` and the `enabled_probe` gate). Probe config is data in owl (`health_tool`, `health_tool_args`, `health_enabled`), validated against the connector's `tools/list` and the tool's `required` inputs (`document/integration-health-check-design.md` §3). No gateway or platform code change is needed; what is needed is that the connector offers a suitable read-only tool and that owl's config for `datto-rmm` points at it.
- Reusable building blocks: `DattoClient.get/put` with token exchange, retry and error mapping (`src/datto_rmm_mcp/api_client.py:27-35,150-157`), `dump_json_capped` (20,000-char cap, `_json.py:12,28`), `error_envelope`, `NO_TOKEN` (`tools/_common.py`), per-request credential isolation via contextvars (`server.py:14-66`).

## Product design

### Goals / Non-goals

Goals
- The agent can start a quick job on a named device with N input variables and gets a job id back (DW1).
- The agent can poll the job and read an unambiguous outcome plus stdout and stderr (DW2).
- A component that fails is reported as failed with its stderr, never as success (DW3).
- Test connection on Datto RMM does a real read-only call (DW4).
- The Bold ICT onboarding SOP's on-prem step can run through these tools in the lab (DW5).

Non-goals
- No callback / webhook to agentos (results are polled).
- No new write operations beyond the existing quick job; no component upload/edit, no device claim.
- No changes to the gateway (`mcp-service-gateway`) or to `mb-platform-agent` code.
- Provisioning the sandbox account, the lab agent, the OU or the service account (environment asks, owned by people named in the Connections comment).
- The SOP 314 flow itself ("Approve new user?" gate) is configured on the platform side; this card only supplies the tools.

### Acceptance criteria

- **AC1 (DW1)**: Given a connected Datto RMM tenant, when the agent lists components and then runs one on a device with two input variables, then Datto receives the variables as name/value pairs inside a quick-job request and the tool returns the job uid.
- **AC2 (DW2)**: Given a started job, when the agent asks for its result, then the answer states the outcome (`running`, `success`, `warning`, `failed`, `pending`, `expired` or `retired`) and, once the job finished, each component's stdout and stderr text.
- **AC3 (DW3)**: Given a component that fails (Datto marks the job or a component `Failure`), when the agent reads the result, then the outcome is `failed` and the stderr text is included; it is never reported as success.
- **AC4 (DW4)**: Given valid or invalid credentials, when Test connection runs, then it performs one real read-only Datto call: valid credentials pass after reading an item, a rejected key/secret reports "credentials rejected".
- **AC5 (DW5)**: On INT with the lab environment, the SOP 314 on-prem step creates one made-up user in the test OU after "Approve new user?", synced to 2qmxyw, with the job result read by the agent; no live system touched.
- **AC6 (safety, from the ticket)**: Credentials never appear in tool output; one tenant's credentials are never used for another tenant's call; running a component still requires `confirm=true`.

### Open questions

1. Datto's exact classification of a "failed" component (non-zero exit code → `componentStatus: Failure`) is assumed from the API's enum, not observed. Does not block implementation; assumption: `Failure` at job or component level means failed. If a sandbox run shows a non-zero exit reported as `Success`/`Warning`, tool text and AC3 need a follow-up (the tool already returns the raw Datto statuses next to the derived outcome so the agent can see both).
2. Which tool owl should use as the Datto probe, and who sets it. Not blocking dev: assumption `health_tool=dattormm_get_components`, `health_tool_args={"max_results": 1}`, `health_enabled=true`, set in the admin console by the gateway owner (Leo Yang) after the INT deploy. DW4 on INT depends on it (see Arch note in the stub).
3. Whether `jobName` must be unique per device. Assumption: not required; the tool generates `MSPbots quick job <UTC timestamp>` by default so each job is distinguishable in the Datto UI.

## Tech design

### Conclusion

Change only `MSPbotsAIFramework/datto-rmm-mcp`. (1) Fix the quick-job request body to the OpenAPI shape and return the job uid at the top level. (2) Add one read-only tool `dattormm_get_job_result` that reads the result endpoint and the stdout/stderr endpoints and derives a single `outcome`. (3) Correct the "no result available" statements in the tool docstrings, server `instructions` and README. (4) Document the recommended owl health-probe settings; no code is needed for the probe. 7 tools after the change.

### Where the current implementation lives

`src/datto_rmm_mcp/tools/jobs.py` (run + status), `src/datto_rmm_mcp/server.py:133-150` (instructions) and `:150-155` (registration), `README.md` Tools table, Known Gaps, Health Check.

### Option analysis

- Result tool shape: (A) one tool `dattormm_get_job_result(job_uid, device_uid)` that returns outcome + both streams; (B) three tools mirroring the three endpoints. Chosen A: the agent needs one call per poll, fewer tools in the catalog, and stdout/stderr are only meaningful together with the status. Not chosen B: more round trips, and the agent must stitch the statuses itself.
- Extending `dattormm_get_job_status` to include results instead of a new tool: not chosen — it is read-only and cheap; the result needs `device_uid` which `get_job_status` does not take, and adding a required argument would break existing callers.
- Probe: use an existing read tool via owl config (chosen, zero code) vs a new dedicated `dattormm_ping` tool (not chosen: duplicates `get_components`/`get_devices`, adds a tool to the catalog only for a probe).
- Free-form `variables` dict is kept as the tool argument (backward compatible with the existing signature `dict[str, str]`) and converted to Datto's `[{name, value}]` list inside the tool; no new parameter for variables.

### Change list

- `src/datto_rmm_mcp/tools/jobs.py`
  - `dattormm_run_component`: build `{"jobName": job_name, "jobComponent": {"componentUid": component_uid, "variables": [{"name": k, "value": v}, ...]}}`; omit `variables` when empty. New optional parameter `job_name: str | None` (default `MSPbots quick job <YYYY-MM-DD HH:MM:SS UTC>`, max 100 chars). Return Datto's response unchanged plus a top-level `job_uid` copied from `job.uid` (when present). Keep `confirm=true` gate and the destructive annotation. Rewrite the docstring: it no longer says results cannot be read; it points to `dattormm_get_job_result`.
  - `dattormm_get_job_status`: docstring says `completed` = finished running, and to call `dattormm_get_job_result` for success/failure and output.
  - New `dattormm_get_job_result(job_uid, device_uid)` (read-only annotation): `GET /api/v2/job/{job_uid}/results/{device_uid}`; derive `outcome` from `jobDeploymentStatus` and the components (rule below); if any component has `hasStdOut`/`hasStdErr` and the job is not `Pending`/`Running`, fetch `/stdout` and `/stderr` once each (not per component — the endpoints return all components). ### Data & API contract

Datto calls (OpenAPI `api/v3/api-docs`, region host from `X-Datto-Platform`/`X-Datto-Api-Url`, unchanged):

```
PUT /api/v2/device/{deviceUid}/quickjob
{"jobName":"MSPbots quick job 2026-11-26 07:40:00 UTC","jobComponent":{"componentUid":"<uid>","variables":[{"name":"UserName","value":"jdoe.test"},{"name":"Ou","value":"OU=Test"}]}}
-> 200 {"job":{"uid":"<jobUid>","status":"active",...},"jobComponents":[{"uid","name","variables":[...]}]}

GET /api/v2/job/{jobUid}/results/{deviceUid}
-> 200 {"jobUid","deviceUid","ranOn","jobDeploymentStatus":"Failure","componentResults":[{"componentUid","componentName","componentStatus":"Failure","numberOfWarnings":0,"hasStdOut":true,"hasStdErr":true}]}
GET .../stdout and .../stderr -> 200 [{"componentUid","componentName","stdData":"<text>"}]
```

Tool output for `dattormm_get_job_result` (example, failed job):

```
{"job_uid":"...","device_uid":"...","outcome":"failed","job_status":"Failure","ran_on":"2026-11-26T07:41:00Z",
 "components":[{"component_uid":"...","name":"Create AD user","status":"Failure","warnings":0,"stdout":"...","stderr":"Access is denied"}]}
```

Errors keep the existing envelope (`not_found` for an unknown job/device, `unauthorized`, `rate_limited`, `invalid_argument`). No DB, no migration, no new header; backward compatible: existing `run_component` arguments keep working (the request body shape changes to the documented one).

### Key flow / sequence

get_devices (hostname) → get_components (name) → run_component(device_uid, component_uid, variables, confirm=true) → job_uid → get_job_status until `completed` (or call get_job_result directly: it reports `pending`/`running`) → get_job_result(job_uid, device_uid) → outcome + stdout/stderr.

### Non-functional

- Idempotency: `run_component` is not idempotent (runs code); unchanged `confirm=true` gate. `get_job_result` is read-only and repeatable.
- Performance: at most 3 Datto calls per result (result, stdout, stderr); stdout/stderr fetched only when the result says they exist and the job finished. Existing retry/backoff on 429/5xx applies.
- Security / multi-tenant: credentials only from request headers, one short-lived HTTP client per call; stdout/stderr come from the customer's own device and are returned as data (they can contain sensitive text — stated in the tool description; the existing prompt-injection note in the README applies); credentials are never echoed into output.
- Observability: errors go through the existing envelope; no new logging of script output.

### Rollout & rollback

Ship as one MCP release via the review leg (merge to `main`, deploy to INT). Backward compatible for callers (one additive parameter, one new tool). Rollback: redeploy the previous `main` commit. DW4 additionally needs the owl probe configuration (below).

### Test strategy

Auto tests with `httpx.MockTransport` for request bodies, outcome mapping (success / warning / failed / pending / running / expired / unknown), truncation, error envelopes, tools/list snapshot and credential isolation. Real-Datto behaviour (the quickjob body being accepted, Datto's failure classification, stdout/stderr content) can only be checked with a sandbox account and a lab device: manual INT cases, marked `data_ready: false`. Regression surface: the other five tools and `tests/test_tools.py` snapshot.

### Effort & breakdown

Story points: 2

Tier 2: one fixed tool and one new tool in a single existing module plus tests and README; external API shape is documented in a machine-readable spec but not field-verified (the unknown that keeps it above 1); one write path (existing); no data migration; the cross-repo piece (owl probe config) is documentation only. Order: fix the run body + tests → add the result tool + tests → docstrings/instructions/README → local run with placeholder headers.

### Risks & dependencies

- Datto's behaviour differs from the spec (e.g. quickjob body rejected, failure not reflected in `componentStatus`): mitigation — raw Datto statuses are returned next to the derived outcome; sandbox cases TC-DATTO-110..112 catch it; README says so.
- DW1, DW2, DW3, DW5 and the live part of DW4 cannot run until the environment asks are met (sandbox account connected to SOP 314, agent on MSPBOTS-ADTEST, test OU and service account).
- DW4 needs owl config for `datto-rmm` (`health_tool`, `health_tool_args`, `health_enabled`), set in the admin console; if left unset the platform keeps showing "Handshake only". No code in the gateway or platform changes.
- The gateway registry README lists `datto-rmm` under a different upstream repo URL (`mcp-service-gateway` README line 61); which repo INT actually deploys for `datto-rmm` is not visible from the gateway source. If INT serves another image, the review leg's `mcppub` publish of this repo is what puts these tools in front of SOP 314 — flagged for the reviewer.
- Release order: no dependency (single repo; owl probe config can be set before or after the deploy — before it is set the status stays `unknown`/"Handshake only", which is today's behaviour).
