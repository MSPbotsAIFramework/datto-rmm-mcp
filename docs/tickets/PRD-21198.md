## Requirement understanding

One line: Monitor devices, resolve alerts, run quick jobs, and manage your Datto RMM fleet from Claude.

The ticket's only content is that one line plus a link to a third-party product page
(`conduit.wyre.ai/plugins/datto-rmm`, fetched for context — it is the marketing page of a
competing MCP connector for Datto RMM, built by WYRE AI; it restates the same sentence as
its headline and otherwise just promotes that vendor's product, with no extra functional
detail). Read literally, the sentence lists four capabilities: monitor devices, resolve
alerts, run quick jobs, manage the fleet. `MSPbotsAIFramework/datto-rmm-mcp` already exists
(built for PRD-16562) and already covers three of the four — device inventory, the
component library, and Quick Job execution. It has no alert-related tool at all. So the
actionable part of this ticket is: add alert visibility and alert resolution to the
existing connector; the rest is already shipped.

## Product design

### Goals / Non-goals

- Goal: an MCP client (Claude, via the MSPbots connector) can list a tenant's Datto RMM
  alerts — across the whole account, or narrowed to one device or one site — and resolve
  a specific alert by its id.
- Goal: alert resolution carries the same explicit-confirmation safety bar as the existing
  destructive tool (`dattormm_run_component`), since it is a one-way action through this API
  (no documented way to reopen a resolved alert).
- Non-goal: muting/unmuting alerts — Datto removed that capability from its own API in
  8.9.0; there is nothing to wrap.
- Non-goal: any other "manage your fleet" admin action (device claim/unclaim, site
  management) — the ticket's own reference page lists exactly "monitor devices / resolve
  alerts / run quick jobs / manage your fleet" and the first, third and (per this design)
  fourth are already met by existing tools scoped to PRD-16562; "manage your fleet" is not
  given a concrete, unmet meaning anywhere in the ticket beyond those three verbs, so it is
  not read as a fourth, separate requirement.
- Non-goal: a cross-account or cross-tenant "all alerts everywhere" view — Datto's API (and
  this server's per-request credential model) only ever expose one tenant's account.

### Acceptance criteria AC1..AC12

- AC1: Given valid Datto credentials, when `dattormm_get_alerts` is called with no
  `device_uid`/`site_uid` and no `status`, then it returns the tenant's account-wide open
  alerts in the same paging envelope shape as `dattormm_get_devices` (`items`, `count`,
  `limit`, `offset`, `has_more`, and `next_offset`/`total_count` when applicable).
- AC2: Given the same setup, when `status="resolved"` is passed, then it returns the
  tenant's resolved alerts instead of open ones.
- AC3: Given a `device_uid`, when `dattormm_get_alerts` is called with it, then only that
  device's alerts are returned (not the whole account's).
- AC4: Given a `site_uid`, when `dattormm_get_alerts` is called with it, then only that
  site's alerts are returned.
- AC5: Given both `device_uid` and `site_uid` are passed together, when
  `dattormm_get_alerts` is called, then it returns the `invalid_argument` envelope and no
  request reaches Datto.
- AC6: Given a result page that the response-size cap cuts short, when
  `dattormm_get_alerts` is called again with `offset` set to the previous call's
  `next_offset`, then no alert is skipped or repeated (same continuation guarantee
  `dattormm_get_devices` already gives).
- AC7: Given a valid `alert_uid` and `confirm=true`, when `dattormm_resolve_alert` is
  called, then it calls Datto's resolve endpoint for that alert and returns Datto's
  response.
- AC8: Given `confirm` is omitted or `false`, when `dattormm_resolve_alert` is called,
  then it returns the `invalid_argument` envelope and Datto's resolve endpoint is never
  called.
- AC9: Given an `alert_uid` that does not exist (or belongs to another tenant), when
  `dattormm_resolve_alert` is called, then it returns the `not_found` envelope, not a crash
  or an opaque error.
- AC10: Given missing or invalid Datto credentials, when either new tool is called, then
  it behaves exactly like the existing tools do today (`NO_TOKEN` / 401 path) — no separate
  credential-handling code is introduced for alerts.
- AC11: Given two different tenants' credentials in use concurrently, when each calls
  `dattormm_get_alerts`, then neither ever sees the other's data or bearer token (the same
  per-request isolation guarantee PRD-21492 already gives the existing tools).
- AC12: Given `tools/list` is requested, then it reports `dattormm_get_alerts`
  (`readOnlyHint`) and `dattormm_resolve_alert` (`destructiveHint`, `alert_uid` required,
  `confirm` optional/defaults false) with the parameters above.

### Open questions

- [Assumed] "manage your fleet" in the ticket's one line is read as already satisfied by the
  combination of device inventory + components + quickjob + (after this ticket) alerts,
  not as a distinct fourth capability — the ticket gives no concrete unmet behavior under
  that phrase, and it is the generic closing clause of the reference page's own marketing
  sentence. If a reviewer disagrees, Goals/Non-goals and AC1–AC12 above are the section to
  redo.
- [Assumed] "resolve alerts" is read as the Datto "resolve" action specifically (the only
  state-changing alert action Datto's API still exposes) — not "acknowledge" or "mute",
  both of which Datto removed from its own API in 8.9.0 and which this server therefore
  cannot wrap even if the ticket had asked for them.
- [Non-blocking] Whether resolving an alert that is already resolved is a no-op, an error, or
  something else is not documented by Datto and was not field-verified (no live tenant
  account in this environment). `dattormm_resolve_alert` passes Datto's response straight
  through either way — see Tech design §7 and the two manual test cases (TC-DATTO-013/014)
  for the real-account verification this still needs before being trusted as fully
  field-correct, exactly the posture the repo already takes with `dattormm_run_component`.
- [Non-blocking] The account-level alert list has no documented "core fields" subset the way
  devices/components do (§ Current state), so `dattormm_get_alerts` returns Datto's alert
  records as-is (size-capped by the existing `dump_json_capped`, no `pick()` trimming).
  If a future ticket shows a safe default subset, trimming can be added then without
  changing the tool's contract.

## Tech design

### Conclusion

Add one new tool module, `src/datto_rmm_mcp/tools/alerts.py`, with two tools
(`dattormm_get_alerts`, `dattormm_resolve_alert`), registered from `server.py` exactly like
the three existing modules. Both tools are thin wrappers over Datto's Alerts API, built
entirely out of the helpers `tools/_common.py` and `api_client.py` already provide — no new
dependency, no change to the HTTP client, auth, or isolation mechanism.

  instructions string the server hands to the MCP client describing its own tools.

### Option analysis

No real alternative for the shape of the two tools — they are the same pattern as
`dattormm_get_devices`/`dattormm_run_component`, in the same repo, over the same kind of
Datto endpoint family, and "follow the existing pattern" is the explicit project
convention this repo already enforces via its own test snapshot and README description
rules. The one real decision point is **tool count/shape**, covered below as it is really
a design choice, not a competing architecture:

| Option | Shape | Why not |
|---|---|---|
| One tool, `status` + optional `device_uid`/`site_uid` (**chosen**) | `dattormm_get_alerts(status, device_uid, site_uid, muted, page, max_results, offset)` | — |
| Separate tools per scope (`dattormm_get_account_alerts`, `dattormm_get_device_alerts`, `dattormm_get_site_alerts`) | 3 tools instead of 1 | Triples the tool surface for what is one underlying query shape differing only by URL; makes the common "show me the open alerts" case (by far the most likely intent behind "resolve alerts") pay a tool-selection cost for free. Rejected per the repo's own precedent: `dattormm_get_devices` already takes optional filters rather than being split into `dattormm_get_devices_by_site` etc. |
| Separate tools per status (`dattormm_get_open_alerts`, `dattormm_get_resolved_alerts`) | 2 tools instead of 1 with a `status` param | Same reasoning; `status` is one more optional parameter, not a second tool, consistent with how `dattormm_get_job_status` does not need a sibling for a different job state. |

No new dependency: `httpx`, `pydantic`, `mcp.server.fastmcp` are already in `pyproject.toml`
and cover everything these two tools need.

### Data & API contract

- `dattormm_get_alerts(status="open", device_uid=None, site_uid=None, muted=None, page=None, max_results=None, offset=None) -> str`
  - Validation: `device_uid` and `site_uid` both set → `error_envelope("invalid_argument", "device_uid and site_uid are mutually exclusive", False)`, no HTTP call (AC5). `status` constrained to `"open"`/`"resolved"` via a `Literal` field (FastMCP's own schema validation rejects anything else before the tool body runs, same mechanism `EnvelopeFastMCP` already wraps for every tool — `_arguments.py`).
  - Endpoint selection: neither id set → `GET /api/v2/account/alerts/{status}`; `device_uid` set → `GET /api/v2/device/{device_uid}/alerts/{status}`; `site_uid` set → `GET /api/v2/site/{site_uid}/alerts/{status}`.
  - Query params: `page`, `max` (same `page_size`/`start_at` arithmetic as devices/components), `muted` passed through when set (Datto's own open-alert filter).
  - Response: `fetch_page(client, path, "alerts", {"muted": muted}, size, start_at(...))`, returned via `dump_json_capped` — same envelope shape as `dattormm_get_devices`: `{"items", "count", "limit", "offset", "has_more"[, "next_offset", "total_count"]}`. `items` are Datto's alert records unmodified (no `pick()` — see Open questions).
  - Errors: `DattoError.to_envelope()` — 401/403 → `unauthorized`, 404 → `not_found`, 429 → `rate_limited`, 5xx/network → `upstream_error`, all via the existing unmodified `_STATUS_TO_CODE` map.
- `dattormm_resolve_alert(alert_uid: str, confirm: bool = False) -> str`
  - `confirm is not True` → `error_envelope("invalid_argument", "Destructive operation requires confirm=true", False)`, no HTTP call (AC8) — identical wording/shape to `dattormm_run_component`'s own confirm gate (`jobs.py:62`).
  - Otherwise: `POST /api/v2/alert/{alert_uid}/resolve`, empty body (per the API documentation; no request payload is used by the resolve action). Uses `DattoClient`'s existing `put`/`_request` machinery — `api_client.py` needs a `post()` passthrough alongside its existing `get`/`put` (one new method, same pattern, no change to retry/backoff/auth logic).
  - Response: `dump_json_capped(result)` on success; `DattoError.to_envelope()` otherwise — 404 (unknown/foreign `alert_uid`) → `not_found` (AC9), satisfied by the existing status map with no change.
  - Backward compatibility: purely additive — no existing tool's request or response shape changes.

### Key flow / sequence

```
Agent: "Which open alerts do we have?"
  -> dattormm_get_alerts(status="open")
  -> GET /api/v2/account/alerts/open?page=0&max=50
  -> {"items": [...], "count": N, "has_more": ..., "next_offset": ...}

Agent: "Resolve alert <uid>, I've confirmed the disk issue is fixed."
  -> dattormm_resolve_alert(alert_uid=<uid>, confirm=true)
  -> POST /api/v2/alert/<uid>/resolve
  -> Datto's response, passed through
```

Both flows go through the same per-request `client_factory()` → `get_client_from_context()`
→ `DattoClient(...)` path every existing tool already uses; no new branch in that chain.

### Non-functional

- Idempotency & concurrency: `dattormm_get_alerts` is read-only, trivially safe to repeat.
  `dattormm_resolve_alert` calling Datto twice for the same `alert_uid` is Datto's own
  behavior to define (undocumented — Open questions); this tool does not add
  client-side de-duplication or a local "already resolved" cache, consistent with the
  repo's stated principle of not caching anything beyond a single request
  (`server.py:20-26`).
- Performance: identical cost profile to `dattormm_get_devices` — one paginated GET, same
  250-record page cap, same 3-retry/backoff policy on 429/5xx (`api_client.py:11-12`).
  `dattormm_resolve_alert` is a single POST, no pagination.
- Security: no new header or credential surface — both tools go through the same
  `X-Datto-Api-Key`/`X-Datto-Api-Secret`/`X-Datto-Platform`/`X-Datto-Api-Url` headers and
  the same per-request `DattoClient`. Cross-tenant access is bounded by Datto's own API
  (a tenant's OAuth token only ever resolves that tenant's own alerts/devices/sites — there
  is no tenant-id parameter this server could get wrong), the same boundary the three
  existing tools already rely on.
- Multi-tenant isolation: unchanged mechanism (`contextvars`-scoped credentials, a fresh
  `httpx.AsyncClient` per call, no shared cookie jar — PRD-21492). AC11/TC-DATTO-011 extends
  the existing isolation test to exercise the new tool so a future regression that
  special-cased alerts' HTTP handling would be caught, rather than assuming the guarantee
  "just carries over" untested.
- Observability: this repo does not emit structured logs today (confirmed — no logging
  setup in `config.py`/`server.py`/any tool module); alerts follow the same pattern as the
  three existing tools. Adding logging across the repo is out of this ticket's scope.

### Rollout & rollback

- Single repo, single change, no feature flag — same rollout shape as every prior PRD on
  this connector (quickjob, paging fixes): merge to `main`, publish to INT via `mcppub`
  (review leg, `mcp-track.md` §4.8), no DB migration, no cross-repo dependency, so
  `release order: any`/not applicable (this is the only repo touched).
- Rollback: revert the merge commit; the two new tools simply disappear from `tools/list`
  on the next deploy. No data was written anywhere this server owns (Datto itself holds the
  alert state), so there is nothing to undo beyond redeploying the previous commit.

### Risks & dependencies

- Risk: the account-level alert endpoints are field-unverified (Open questions, §
  Current state) — if a real tenant's response shape differs from the documented one (e.g.
  a different pagination envelope key than `pageDetails`), `fetch_page`'s generic handling
  of `pageDetails`/`nextPageUrl` (`_common.py:33-37`) already tolerates either shape the
  same way it does for devices/components, so the blast radius of a mismatch is "wrong

### Pre-existing bug found and fixed while wiring the new module in

`server.py`'s `client_factory() -> DattoClient | None` return annotation was
evaluated eagerly against the module's own `DattoClient` name on every
`create_mcp_server()` call. Any test that monkeypatches `server.DattoClient`
to a `functools.partial` (the repo's own established fixture pattern,
`test_paging.py`/`test_isolation.py`) hit `TypeError: unsupported operand
type(s) for |: 'functools.partial' and 'NoneType'` before the test body ever
ran. This was pre-existing and baseline-red (15 of 40 pre-change tests
failed this way) — found because the new alerts tests reuse the exact same
monkeypatch fixtures and would otherwise have been blocked from running at
all. Fixed with `from __future__ import annotations` (zero behavior change,
standard idiom); commit `1d0133b`.
